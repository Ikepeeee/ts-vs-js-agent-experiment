# 型注釈と型検査がAI生成コードの残存バグに与える影響：実験設計

Oct 27, 2026 · @Toru Ikeda

英語版：`experiment-design.md`。正本は英語版で、食い違う場合は英語版に従う。

## 目的とリサーチクエスチョン

TypeScriptとJavaScriptの中だけで、「型注釈」と「型検査のフィードバック」を別々にオン・オフし、AIエージェントが書いたコードに**検証ループを通過した後も残るバグ**がどう変わるかを測る。PythonやRustなど他の言語とは比べないので、言語どうしの学習データ量の差は比較に入らない。

- **RQ1（主）：** 型検査のフィードバックは、残存バグを減らすか。
- **RQ2：** 型注釈は、検査しなくても「文脈」として残存バグを減らすか。
- **RQ3：** それぞれの効果は、時間とトークンのコストに見合うか。
- **RQ4（探索的）：** 効果は、変更が広く波及する課題ほど大きいか。

TypeScriptとJavaScriptはこの設計と相性がよい。Node.jsは型注釈を消してTypeScriptをそのまま実行できるので、「注釈は書くが検査しない」条件を実行環境を変えずに作れる。JavaScriptのファイルもTypeScriptの検査器で推論による検査ができるので、「注釈なしで検査あり」も同じ検査器で作れる。遠藤さんのベンチマークにJavaScriptとTypeScriptの結果があり、比較の基準にもなる。

ただし、TypeScriptとJavaScriptでは学習データの分布が完全には同じではない。この差は型注釈の要因（A）の効果に混ざる。型検査の要因（F）は同じファイル形式の中で比べるので、この影響を受けない。

## 仮説

実行前に、次の4つを事前登録する。方向も含めて先に書き、結果を見てから変えない。

| ID | 仮説 | 対応するRQ |
| --- | --- | --- |
| H1 | 型検査のフィードバックがあると、隠しテストの失敗率が下がる | RQ1 |
| H2 | 型注釈だけ（検査なし）では、失敗率はほとんど変わらない | RQ2 |
| H3 | 型検査のフィードバックは、時間とトークンを1.3倍以上に増やす（参考：遠藤さんの結果では、TypeScriptのコストはJavaScriptの約1.6倍） | RQ3 |
| H4 | H1の効果は、小さな機能追加（T2）より、モジュールをまたぐ変更（T3）で大きい | RQ4 |

H2は「差がない」という仮説なので、有意でないことではなく、効果量の95%信頼区間が事前に決めた範囲（オッズ比 0.8〜1.25）に収まるかで判定する。試行数が少ないので、この範囲に収まらず「判定不能」になる可能性が高い。その場合もそのまま報告する。

「型検査の効果は、単に見直しの量が増えたせいではないか」を確かめる対照条件（C-review）は、今回は外して第2段階に回す。

## 実験条件

「型注釈（A）」×「型検査のフィードバック（F）」の2×2の4条件で行う。注釈なしはJavaScript、注釈ありはTypeScriptで書かせる。

| 条件 | ファイル形式 | 型検査のフィードバック | 役割 |
| --- | --- | --- | --- |
| A0F0 | JavaScript | なし | 基準（素のJavaScript） |
| A0F1 | JavaScript | あり（`tsc` の `checkJs` による推論だけの検査） | 注釈なしでの型検査の効果 |
| A1F0 | TypeScript（Node.jsが型を消して実行） | なし | 注釈が「文脈」として効く効果 |
| A1F1 | TypeScript | あり（`tsc`） | 型付き開発の全部入り |

**型注釈（A）の操作**

- A1：`.ts` ファイル。開始時のコードは注釈つきで、「すべての関数の引数と戻り値に型を書く」と指示する。Node.jsがそのまま実行できるよう、型を消すだけで動く構文に限る（`enum` や `namespace` は使わない）。
- A0：`.js` ファイル。同じTypeScriptのコードから、型を消すツール（ts-blank-spaceなど）で注釈だけを取り除いたものを渡す。中身の処理は同一に保つ。「型は書かない（JSDocの型コメントも書かない）」と指示する。

**フィードバック（F）の操作**

- F1：編集のたびに `tsc --noEmit` を自動で実行し、結果をエージェントに返す。型エラーが0になるまで終了できない。設定はA0とA1で共通にし、`strict` に、A0では `allowJs` と `checkJs` を加える。JavaScriptへの検査は推論が中心になるので、誤検出の量をパイロットで確かめる。
- F0：コンテナにTypeScriptのコンパイラを入れず、型への言及もしない。A1F0では型の誤りがあってもそのまま実行され、振る舞いに出たときだけテストで見つかる。

**全条件に共通**

- ESLint（推奨ルール。型情報を使うルールは除く）と見せるテストは、すべての条件で使える。未定義の変数などは型検査なしでも捕まるので、測るのは「現実的な開発環境に型検査を足したときの上乗せ分」である。
- プロンプトの差は、上の条件ごとの指示の1〜2文だけにする。全文を公開する。

## 課題の設計

既存コードの変更を2課題行う。型が効くとされるのは変更の場面で、新規実装は遠藤さんの結果（600回中597回が合格）から差が出にくいと予想されるので、今回は外す。

| 課題 | 種類 | 内容 | 開始時のコード | 見込みの規模 |
| --- | --- | --- | --- | --- |
| T2 | 既存コードへの機能追加 | 遠藤さんの簡易Gitに `branch`・`merge`（早送りのみ）・`tag` を追加 | 固定した参照実装 | 約400行 |
| T3 | モジュールをまたぐ変更 | 自作の小さな予約管理APIで、予約のデータ型に必須項目（タイムゾーンつきの時間帯）を足し、利用側をすべて追従させる | 固定した参照実装 | 2千〜3千行 |

- **T2** は、既存の内部APIを正しく使えるかを問う。簡易Gitの参照実装（v1・v2相当）は自分で用意する。
- **T3** は、データ型の変更が広く波及する、型が最も効くはずの課題。Node.js標準の `http` とメモリ上のストアだけで作り、外部サービスにはつながない。自作なので、モデルの学習データには含まれない。
- 参照実装はすべてTypeScriptで書き、JavaScript版は型を消すツールで作る。両者の処理は同一である。
- 外部ライブラリは実行時には使わない。開発用の道具（ESLint、F1のみ `typescript`）は版を固定する。
- 仕様書は条件にかかわらず同一。型についての記述は含めない。
- 参照実装は先に完成させ、変更後の版も自分で作って全テストに合格することを確かめておく（課題として解けることの確認）。

## エージェントと実行環境

1試行ごとに新しいコンテナを立ち上げ、条件による違いは「使える道具」「ファイル形式」「指示の1〜2文」だけにする。

- **エージェント：** Claude Codeを非対話モード（`claude -p`）で、Claudeの定額プランの範囲で動かす。
- **モデル：** Sonnet級のモデルをIDまで固定して使う。利用上限の消費が少なく、最上位モデルより失敗率が高めになるので、少ない試行でも差が見えやすい。最上位モデルでの追試は第2段階に回す。
- **コンテナ：** イメージはダイジェストで固定。Node.jsは型を消しての実行が標準で有効な版に固定する。ESLintと、（F1のみ）TypeScriptのコンパイラも版を固定して入れる。テストはNode.js標準の `node:test` で動かす。外部への通信はClaudeとの通信以外遅断する。
- **F1の仕組み：** Claude Codeのフックで、ファイル編集のたびに `tsc --noEmit`（差分ビルド）を実行し、結果を返す。終了時のフックで、型エラーが残っていれば終了を拒否する。
- **終了条件：** 見せるテストにすべて合格し、F1では型エラーが0。または上限切れ。
- **試行ごとの上限：** 全条件共通で、ターン数と経過時間に上限を設ける（目安：50ターン、30分。パイロットで確定）。上限に達した試行も除外せず、その時点のコードを評価する。
- **記録：** 会話ログ全文、経過時間、ターン数、最終の差分、F1では各時点の型エラー数。コストは `--output-format json` の出力から、入力・出力トークン数とAPI料金換算の推定額を記録する。
- **実行順：** 条件と課題の組み合わせを乱数で並べ替え、同じ期間に混ぜて実行する。利用上限で途中で止まった試行は破棄して同じ順番でやり直し、破棄した件数も報告する。
- 実行の定義は、Laskで型付きのタスクとして書けば、試行の再現性をそのまま公開物にできる（任意）。

## テスト設計：見せるテストと隠しテスト

課題ごとに完全なテスト一式を先に作り、**乱数で半分に分けて**、片方だけをエージェントに見せる。どこにテストの穴を開けるかを実験者が選べないようにするためである。

**テスト一式の作り方**

- 仕様に基づくブラックボックステストにする。T1・T2はCLIの入出力、T3はHTTPの要求と応答だけを見る。内部の型や関数名に依存させないので、TypeScriptとJavaScriptで有利不利が出ない。
- テストは型なしのJavaScriptで書き、`node:test` で実行する。
- 中身は3種類：仕様の具体例、境界ケース（空のリポジトリ、日本語ファイル名、日付をまたぐ予約など）、性質ベーステスト（fast-check。例：コミットしてから `checkout` すると元の内容に戻る、予約の時間帯は重ならない）。
- AIに下書きさせてもよいが、必ず自分でレビューし、参照実装ですべて合格することを確かめる。
- 参照実装に対してミューテーションテスト（StrykerJS）を回し、「見せるテストだけ」と「全体」の検出率を記録する。見せるテストがどれだけ穴だらけかを、数字で示すためである。

**分け方と管理**

- 機能（コマンドやエンドポイント）ごとに層を分けて抽出し、どの機能にも見せるテストと隠しテストが両方あるようにする。乱数の種は公開する。
- 分け方は全条件・全試行で同一。
- テスト一式は本実験の前に凍結し、ハッシュを事前登録に載せる。後から一切足さない。
- 隠しテストはコンテナに入れず、試行の終了後に別の環境で実行する。
- 見せるテストは読み取り専用にし、終了時にハッシュを照合する。テストを弱めて通す行為を防ぐ。
- 隠しテストは一切型検査をしない。A1の成果物もNode.jsで型を消して実行し、振る舞いだけを判定する。

## 評価指標

主指標は「隠しテストの失敗率」の1つだけにし、それ以外はすべて副指標として事前に区別しておく。

| 区分 | 指標 | 定義 |
| --- | --- | --- |
| 主 | 隠しテストの失敗率 | 1試行の最終コードで失敗した隠しテストの数 ÷ 隠しテストの総数 |
| 副 | 残存バグの有無 | 隠しテストを1つでも落とした試行の割合 |
| 副 | コスト | トークン数（入力・出力）、API料金換算の推定額（ドル）、経過時間（秒）、ターン数 |
| 副 | 完了率 | 上限内に終了条件を満たした試行の割合 |
| 副 | 潜在する型エラー | F0の最終コードを試行後に `tsc` で検査した型エラー数（記述のみ。検定はしない） |
| 操作の確認 | 型注釈の被覆率 | A1で型が付いた関数の割合、A0でJSDocの型コメントが混ざった数 |
| 操作の確認 | テスト改変の試み | 見せるテストへの書き込みの試みの回数 |

**バグの中身の分類（探索的）**

- 隠しテストの失敗を無作為に約100件抽出し、原因を4種類に分ける：インターフェース・型の食い違い、ロジックの誤り、仕様の誤解、境界ケースの見落とし。
- 分類するときは条件を伏せる。A1のコードも型を消してから読むので、見た目で条件が分からない。
- 型が効くなら「インターフェース・型の食い違い」だけが減り、他は変わらないと予想する。

## 試行回数と統計解析

本実験は2段階で行う。まず4条件×2課題×各10回の80試行を実行し、事前に決めた基準で結論が出なければ、各10回を足して最大160試行にする。

**回数の決め方**

- 各条件20回でも、検出できるのは大きな差（基準条件の失敗率が十分高く、それが半分になる程度）だけである。小さな差は「検出できなかった」として報告し、「差がない」とは言わない。
- パイロットでA0F0の失敗率を測る。失敗率が低すぎる（目安は試行の2割未満しか隠しテストを落とさない）場合は、本実験の前に課題を難しくする。本実験の途中では課題を変えない。
- 中間解析は1回だけ。H1の主効果のp値が0.005未満なら、効果ありとして停止する。それ以外は続行し、最終解析の有意水準を約0.048とする（O'Brien–Fleming型の配分）。この基準も事前登録する。

**解析の方法**

- 主解析は、隠しテスト1件ごとの合否を目的変数とする一般化線形混合モデル（ロジスティック）。固定効果は注釈（A）、フィードバック（F）、A×F、課題。変量効果は試行とテスト項目。試行数が少ないので、試行ごとの失敗をテスト項目の単位で数えて情報を稼ぐ。
- 結果は、p値だけでなくオッズ比と95%信頼区間で報告する。
- 事前に決める比較は3つ。H1：A0F1対A0F0、A1F1対A1F0。H2：A1F0対A0F0。多重比較はHolm法で補正する。
- H4（課題による違い）は、F×課題の交互作用で見る。探索的なので、補正の対象外として区別して報告する。
- コスト（H3）はトークン数と経過時間の対数をとって比較し、倍率として報告する。
- 上限切れの試行も主解析に含める。それらを除いた結果も、感度分析として並べて示す。

## 妥当性への脅威と対策

最大の弱点は、型注釈の効果（A）にTypeScriptとJavaScriptの学習データの違いが混ざることだ。主の問いである型検査の効果（F）は、同じファイル形式の中で比べるので影響を受けない。

| 脅威 | 内容 | 対策 |
| --- | --- | --- |
| 学習データの偏り | TypeScriptとJavaScriptではコードの年代や分野の傾向が違う | Fの比較は同じ形式内で行う。Aの結果は「注釈＋形式の違い」として解釈する |
| 試行量の差 | F1は長く考える分、単に見直しが増えたせいかもしれない | トークン数を記録して差を示す。対照条件（C-review）は第2段階で足す。試行ごとの上限は全条件で揃える |
| 実験者による誘導 | テストの穴の開け方で結果が変わる | 乱数で分割し、種とハッシュを事前登録する |
| 隠しテストの漏えい | エージェントが隠しテストを見てしまう | コンテナに入れず、仕様書にも含めない |
| 指示の無視 | A0でJSDocの型を書く、A1で注釈を省く | 型注釈の被覆率を測って報告する |
| テストを弱めて通す | 見せるテストを書き換える | 読み取り専用にし、終了時にハッシュを照合する |
| モデルの変化 | 期間中にAPI側の挙動が変わる | モデルIDを固定し、条件を乱数の順で混ぜて実行する |
| ESLintとの重なり | 型検査なしでも未定義の変数などは捕まる | 全条件で同じESLintを使い、「上乗せ分」として解釈する |
| 一般化の限界 | 変更課題2つ、Sonnet級の1モデルだけ | 結論は「この規模のTypeScript・JavaScript」に限ると明記する |
| 実験者の好み | 実験者自身が型の効果を期待している | 事前登録と、生データ・解析コードの全公開 |

## 実施手順と事前登録

本実験の前にテストと解析計画を凍結し、公開してから実行する。平日夜2時間で、およそ8週間を見込む。

1. **第1〜2週：課題の準備。** T2・T3の参照実装（TypeScript）と変更後の正解版、JavaScript版、仕様書、テスト一式を作る。
2. **第3週：実行基盤。** コンテナ、F1のフック、記録、隠しテストの評価環境を作る。
3. **第4週：パイロット。** 4条件×T2・T3で各2回の16試行。基盤の不具合、A0F0の失敗率、試行ごとの上限、JavaScriptへの `tsc` 検査の誤検出、定額プランで1日に回せる試行数を確かめる。パイロットのデータは本解析に使わない。
4. **第4週末：事前登録。** 仮説、主指標、比較、回数、中間解析の基準、解析コード、テストのハッシュ、乱数の種を、タグ付きのコミット（またはOSF）で公開する。
5. **第5〜7週：本実験。** 乱数の順に、利用上限の範囲で夜間に少しずつ自動で実行する。80試行で中間解析し、必要なら残り80試行を回す。
6. **第8週：解析と執筆。** 事前登録どおりの解析、条件を伏せたバグの分類、公開用の文章。

## 予算

Claudeの定額プランの範囲で回すので、追加の費用はほぼかからない。制約はお金ではなく利用上限で、それが実験の日数を決める。

| 段階 | 試行数 | 内訳 |
| --- | --- | --- |
| パイロット | 16 | 4条件×2課題×2回 |
| 本実験・第1段 | 80 | 4条件×2課題×10回 |
| 本実験・第2段（必要な場合のみ） | 80 | 4条件×2課題×10回 |
| 合計 | 96〜176 | 当初案の約300試行から半分以下 |

- 1日に回せる試行数はパイロットで測り、本実験の日程をそこで確定する。
- コストの指標はトークン数と、そのAPI料金換算の推定額で報告する。実際に支払った額ではないことを明記する。
- 利用上限で日数が大きく延びる場合は、第2段だけAPIで回すことも検討する。その場合もモデルIDと設定は変えない。

## 成果物と公開

結果がどちらに出ても公開する。「差がない」も、まだ誰も測っていない領域では情報になる。

- **リポジトリ：** 課題と仕様書、参照実装、実行基盤、解析コード。隠しテストは本実験の終了後に公開する。
- **生データ：** 全試行の会話ログ、差分、隠しテストの結果、コスト。
- **事前登録：** 本実験の前に公開した版と、最終報告との差分。
- **記事：** 日本語と英語で。遠藤さんのベンチマークの「残るバグは測っていない」という空白を埋めるものとして位置づける。
- **再利用できる仕組み：** 隠しテストで残存バグを数える実行基盤は、AI時代のテストフレームワークの構想の中核にそのまま使える。

第2段階の候補：試行量を揃える対照条件（C-review）の追加、新規実装の課題（簡易Git v1・v2）、最上位モデルでの追試、より大きな実リポジトリでの変更課題、Python（pyright）での同じ設計の追試。
